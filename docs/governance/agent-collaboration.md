# Agent 协作与执行规则

本文承接 `AGENTS.md` / `CLAUDE.md` 不适合在启动时全量加载的协作细则，面向人工与 AI 协作者。目标是说明任务如何定界、实施、验证和交接；不承载当前阶段、临时门禁、产品专题设计、历史流水或远程状态快照。

## 文档职责与优先级

### 三层职责

| 层级 | 职责 | 典型内容 |
| --- | --- | --- |
| 根入口 | 启动即生效的长期契约 | 授权边界、高风险红线、工作区保护、任务路由 |
| `docs/` 专题 | 稳定但按任务读取的规则和设计 | 产品、架构、安全、法规、验证、治理与协作细则 |
| 当前状态与记录 | 会随阶段变化的状态和事实 | 当前顺位、临时门禁、“当前不做”、批次证据 |

根入口不是项目手册的副本，`docs/README.md` 也不是阶段规则正文。入口负责告诉读者“去哪里读”，专题负责解释“长期规则是什么”，状态与记录负责说明“现在处于什么阶段、已经发生了什么”。

### 判断顺序

1. 先遵循适用法律、许可证、安全披露边界和用户在当前任务中的明确要求。
2. 按[仓库治理](repository-governance.md)的规则层级确定产品、架构、当前状态和专题真相源。
3. 遵循 `AGENTS.md` / `CLAUDE.md` 的启动级约束，并按本文执行详细协作流程。
4. 通过代码、测试、配置、自动化和实际环境确认实现事实。
5. 文档与实现或远程状态不一致时，先判断哪一侧过期，再在授权范围内统一口径；不通过放宽检查或静默选择制造表面一致。

## 任务推进

### 开始任务

- 运行 `git status --short --branch`，确认实际分支、ahead / behind、暂存区、工作树和未跟踪文件。
- 区分本任务改动、用户已有改动和可能的并行改动，只把任务范围内文件纳入修改、验证、暂存和提交。
- 明确请求属于说明、诊断、设计、实现、治理、发布还是监控；一种授权不自动包含相邻操作。
- 先读当前状态和文档索引，再按任务进入最少必要专题；只有追溯证据时才展开研究、测试记录或归档。
- 识别法规、安全、身份、密钥、升级、协议、持久化、许可证、依赖、用户数据和外部状态影响，并按[仓库治理](repository-governance.md)确定风险等级。
- 修改前查找已有实现、测试、脚本、命名和目录惯例，不另造无必要的入口、helper、配置口径或兼容层。

### 范围与批准

- 用户明确要求修改且边界清楚、风险可控时，直接实施并完成风险匹配的验证。
- 只要求分析、解释、诊断、审查或建议时，不修改文件、提交或远程状态；诊断授权不自动包含修复。
- 不同合理解释会明显改变用户行为、架构、安全、数据模型、兼容性、许可证或外部影响时，先说明关键判断并请求选择。
- 已确认方案若发生实质性范围变化，应暂停扩张并重新确认，不把变化隐藏在实现细节中。
- L0 可以直接实施并精准验证；L1 需要对应静态检查和精准测试；L2 先确认专题或 ADR 边界并覆盖兼容与失败模式；L3 必须单独说明并取得当前任务授权。
- 风险等级决定审查和验证深度，不扩大任务授权；历史会话、笼统长期授权和相邻动作授权均不沿用。

### 实施与收口

对于需要多步验证的任务，优先准备完整且有界的工作包，明确设计、实现、运行、结果复核各自是否已授权。所有者可以在同一次明确授权中列出多项精确动作、命令顺序、允许次数、网络/设备范围、总资源预算、停止和清理方式；包内已授权且前置满足的步骤无需人为拆成反复确认。未列出的外部写入、重跑和清理仍不包含在内；既有单次实验合同、硬停止线与实质范围变更要求不能被笼统工作包覆盖。

- 优先解决根因和边界问题，交付小而完整的真实纵向切片，不以占位、演示路径或玩具式最小实现冒充完成。
- 在满足需求和质量的前提下控制修改范围；不混入无关重构、格式化、依赖升级或目录搬迁。
- 相邻问题只有在直接阻断当前目标或用户明确扩展范围时处理；可分割步骤完成后执行对应最小验证。
- 抽象必须减少真实重复、隔离稳定边界、降低复杂度或表达明确领域概念，不为未来可能需要预建空框架。
- 不用异常吞噬、默认成功、无边界重试或多层 fallback 掩盖失败；所有兜底都应有明确触发条件、可观测性和停止线。

## 工作区与文件保护

- 已暂存、未暂存、未跟踪和其他协作者写入的内容默认属于用户，不覆盖、不回滚、不顺手提交。
- 修改与现有差异重叠时先理解用户改动并做最小兼容编辑；无法安全合并时停止写入并说明冲突，不以重写整文件规避判断。
- 不用 reset、checkout、rebase、清理命令或批量格式化制造预期工作区，也不为通过门禁改写第三方材料、上游镜像或生成文件。
- 临时脚本、日志、截图、测试数据和调试产物放入任务专用且已忽略的位置；只清理本任务创建且确认无保留价值的内容。
- 未经明确授权不跨工作区修改兄弟项目、参考仓库或其他本地项目；读取参考资料不自动授权写入。
- 破坏性操作前解析并复核精确目标；不得以仓库根、用户目录、未解析变量或宽泛 glob 作为递归删除、覆盖或批量移动目标。
- 修改后复核 `git diff`、`git status` 和未跟踪文件，确认没有越界文件、秘密、缓存、意外换行、权限变化或测试产物。

## 实现、依赖与数据

- 命名应表达领域职责，不新增含义不清的缩写、空泛 `Manager` / `Helper` / `Context` / `Adapter` 或只包装技术动作的抽象。
- 错误应保留上下文和真实原因；控制流优先早返回、显式分支和小而清晰的函数，避免深层嵌套、无意义转发方法和隐藏简单逻辑的 wrapper。
- 单个源码文件接近 `1000` 行时评估按职责拆分，原则上不继续超过 `1500` 行；生成文件和有来源的上游材料除外。
- committed 相对路径默认不超过 `180` 个字符，单文件默认不超过 `10 MiB`；目录按浅层职责分组，不用深层树编码长自然语言语义。
- 公共协议、持久化格式和外部接口必须有版本或明确演进策略，并覆盖兼容、迁移、未知字段、拒绝路径、资源上限和失败恢复。
- 标准库或现有依赖能够清楚解决问题时不新增依赖；新增时说明用途、版本、维护状态、许可证、供应链风险和可替代方案。
- 依赖声明与 lockfile 必须由对应包管理器维护，不手工伪造解析结果；意外 lockfile 漂移必须查明原因。
- 第三方代码、固件、数据、模型、字体、图标和资产必须记录来源、版本、许可证、必要归属和更新路径；公开可访问不等于可以复制或再分发。
- 生成代码、绑定、schema、fixture、固件清单和测试向量应能追溯生成入口与输入，并说明再生成方式和人工修改边界。
- 测试、文档和示例只使用合成或脱敏数据，不复制真实通信、设备凭据、安全报告、专有输入或生产秘密。
- 仓库自有文本遵循 `.editorconfig`、`.gitattributes` 和 `.gitignore`；新增或修改 Markdown 后检查相对链接，新增 JSON 后验证语法。

## 外部环境与高风险操作

- 射频发射、固件刷写、依赖安装或更新、系统配置、长期服务、桌面应用、浏览器或虚拟机启动、远程设置、发布、签名和真实设备或用户数据操作均按 L3 处理。
- 执行前说明精确命令或操作、目标、主要副作用、预计持续时间、证据留存方式和清理或回滚方案，并取得当前任务的明确授权。
- 授权只覆盖已说明的命令、范围和影响；命令、依赖、端口、设备或运行方式发生实质变化时重新确认。
- AI 启动的长期进程在任务结束前按约定关闭并报告；用户自行启动的进程不擅自停止。
- 沙盒、权限、PATH、网络、证书或平台差异导致关键验证失败时，保留原始错误并识别环境特征；必要时申请在更真实环境复验同一命令，不修改产品代码适配异常环境。
- 提权只用于已说明的验证或已授权操作，不扩大文件、依赖、系统、设备或远程修改范围。
- 射频操作还必须遵循[无线电合规前置条件](../regulatory/radio-compliance.md)和当前状态；身份、密钥与通信数据操作还必须遵循 `docs/security/` 和 `SECURITY.md`。

## 文档与证据

- 当前状态只保留结论、关键阻塞、下一项决策与停止线；完整历史流水移入有日期的记录，注明截至时点并保留引用。规范不重复当前 run/hash，索引只描述文档用途。
- 更新状态时搜索其他专题的“当前”“未执行”“未授权”等时态；历史阶段用日期或单元明确限定，避免把已消费的单次授权写成尚未执行或持续有效。
- 被 runner 固定 revision/SHA 的合同不作为普通文档整理对象；修订需说明消费者、版本与重新验证影响，不能为链接或措辞清理破坏原合同。
- 非实现者复核须说明复核范围、参与历史、方法和能力限制。工程证据复核、密码安全审计、法规与法律意见分别记录；独立 Agent 的结果不自动等同于专业资质意见。

- 优先更新已有正式文档；入口只保留短说明、当前结论和索引，历史推演、命令流水和长背景进入专题、记录或归档。
- `docs/research/`、测试记录和归档只保存证据，不自动成为产品承诺、架构决策或 Accepted ADR。
- 新增或大改长文档时说明用途、目标读者和明确非目标，不让单个文件同时承担入口、规范、历史流水和完整参考。
- 引用兄弟项目时使用项目名和稳定在线地址；任务临时提供的本机绝对路径不得进入长期文档。
- 项目日期统一使用 Asia/Shanghai（UTC+8）。
- 产品目标、架构候选、Accepted ADR、厂商声明、第三方结果、台架结果和 RadishLink 实测必须明确区分；证据词汇以[仓库治理](repository-governance.md)为准。
- 距离、速率、时延、功耗等数字必须保留条件或目标属性；PHY 峰值、标准上限、第三方结果和实测应用指标不得混写。

## 验证策略

- 文档改动至少运行 `./scripts/check-repo.sh` 和 `git diff --check`；Windows 变更或跨平台验收时再执行 `pwsh ./scripts/check-repo.ps1`。
- 实现改动还需执行对应格式化、静态检查、精准测试和必要的三节点集成验证；L2 变更覆盖适用的正例、负例、兼容性、迁移、降级、资源上限和失败恢复。
- 修复缺陷时优先加入能暴露原问题的回归用例；无法自动复现时记录人工复现条件和证据限制。
- 命令成功退出不自动代表目标达成，仍需检查产物、状态变化、诊断、负向结果和残留进程。
- 验证失败时保存命令、退出码和关键错误，再判断代码、数据、测试、工具或环境根因；不得只因重跑成功就忽略不稳定性。
- 静态检查、mock、headless、仿真、台架或两节点结果只证明其覆盖条件，不替代外场、量产、法规、三节点、多跳、平台行为或人工可见结果。
- quick / fast 模式只用于开发反馈，不自动替代阶段合并、发布或高风险变更的正式门禁。
- PR、交接和测试文档只记录实际执行的验证；未执行、失败、受环境阻塞和需人工或实验室完成的项目分别说明。

## Git 与远程状态

- 未经明确要求不提交、push、创建 PR、tag、Release、Ruleset 或部署；commit 授权不包含任何远程写入。
- 未经明确要求不 amend、重写、合并或拆分既有提交，不修改用户 Git 身份，也不使用破坏性操作处理共享历史。
- 提交使用 Conventional Commits，按可审阅主题拆分，不添加 AI 协作者署名；暂存前复核完整 diff，存在无关改动时按精确路径暂存。
- 提交后复核提交摘要、工作区和相对远端的 ahead / behind；分支、合并、回流、Ruleset 与 CI 细节以[仓库治理](repository-governance.md)和 [ADR 0003](../adr/0003-branch-pr-and-ruleset-governance.md)为准。
- 远程 Ruleset、workflow 和本地模板只有在远程实际启用并复核后，才可描述为已生效。

## 完成与交接

- 先说明实际结果，再列关键文件、已执行验证和仍未关闭的风险。
- 明确区分已完成、未执行、受环境阻塞和需要人工或实验室处理的项目。
- 报告假设、兼容性影响、失败模式和结论仍不覆盖的环境。
- 报告工作区是否干净，是否存在未提交或未推送提交、后台进程和任务专用临时产物。
- 报告远程分支、Ruleset、PR、Release 等外部状态是否真实改变；本地模板不能替代远程事实。
- 只有任务范围内必要工作和风险匹配验证已经完成时才表述为“完成”；待授权动作和关键验证阻塞必须显式保留。

## 根入口维护

一条规则只有同时满足以下条件，才应加入 `AGENTS.md` / `CLAUDE.md`：

1. 跨任务成立，而不是某个功能或批次专属。
2. 跨开发阶段成立，不会随当前里程碑自然失效。
3. 必须在协作者读取专题前生效，否则容易造成高风险或大范围错误。
4. 无法仅通过清晰的任务路由和对应 `docs/` 专题可靠承载。

不满足这些条件的内容应归入专题、当前状态、记录或归档。两个根入口必须逐字一致；修改任一文件时同步另一份并执行仓库检查。根入口应保持短、稳定和可路由，`docs/README.md` 应保持为文档索引而非规则正文。
