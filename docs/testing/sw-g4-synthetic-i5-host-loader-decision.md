# I5 宿主可行性裁决与真实 FD loader 合同草案

更新日期：2026-10-18。

本文面向所有者、环境实施者和加载链复核者，承接[宿主写入边界与原生生命周期](sw-g4-synthetic-i5-host-delivery.md)。用途是判断当前承载能否进入实施、列出替代路线，并约定真实加载必须证明什么。它是待接受的设计草案，不是 Accepted ADR、实现、环境操作单或验收结果。

## 本包范围与裁决

上一包 28 个文件已提交为 `fa48743`，未 push。所有者本次仅授权宿主可行性决策与真实 FD loader 合同设计，以及不满足时的替代方案和待决策事项；不实现、不启动 VM、不安装依赖、不提交或 push，全部真实入口保持 STOP。本次只读取仓库和公开一手机制资料，不查询当前 VM/宿主运行状态，也不改变系统配置。

**当前 Mac/UTM 在现有完整写入合同下为 NO-GO，继续 `blocked-host-system-writes`，不能作为达标环境放行。** 原因包括已知可写路径未受硬边界约束、宿主系统写入缺少完整机制和观察，以及准备期总包络尚未获批。该裁决不是“已实测超额”，也不是证明所有未来 macOS 配置永远不可能满足；本次没有新的物理实测。

继续补 JSON、增加库包校验或完成 loader 都不会关闭宿主阻塞。既有纯校验报告中的 `consistency_passed` 只证明声明一致。所有真实授权/物理通过/I5-ready 标志继续保持既有语义，不能因为本设计选了候选机制而置 true。

## “现有预算”包含两个不同问题

| 合同 | 现有数值与归属 | 本包裁决 |
| --- | --- | --- |
| 正式 I5 整批 | build 256、daemon 160、evidence 240、diagnostic 64、三节点 tmpfs 48 MiB，合计 768 MiB | 不增加、不跨批重新发放；完整设备 D 加该域额外硬预留 H 必须小于等于域上限 C |
| preparation 局部上限 | input 至多 256 MiB，WORK 128 MiB，RESULT 8 MiB，host-retention 至多 32 MiB | 四项上限合计 424 MiB，但这不是已批准的完整准备期预算；input 同时容纳 APT 与 library 的完整介质 |
| preparation environment / 总包络 | schema 要求显式正整数，但没有给 environment 固定获批额度；具体完整 envelope 仍须评审 | 不填任意大数制造通过，也不能默认借用正式 I5 的 768 MiB；缺数值即不能批准执行 |
| 初始化根 | 至多 1 MiB / 1024 inode 的独立 noswap tmpfs | 是已有 environment 内的子预留，不能给 loader 解包、缓存或日志使用 |
| 时间 | 宿主保守合计 897 秒、绝对至多 900 秒；guest 至多 540 秒；单 RPC 至多 2 秒 | loader 必须分割已有窗口，不能增加一次完整启动/初始化时间 |

以上数值来自[容量评审实现](../../scripts/sw_i5_preparation_plan.py)、[隔离合同](../../scripts/sw_i5_preparation_isolation.py)和[正式 I5 资源合同](sw-g4-synthetic-i5-resource-isolation.md)。准备期需满足 `Σ C_domain ≤ envelope`；每域 `D + Σ H ≤ C`，组件峰值和各物理域的硬预留不得重复认领。未知项不能当零，空间余量采样不是硬边界。

若正式 I5 的四个整盘 D 取满 256/160/240/64 MiB，磁盘域留给 H 的总空间就是零；已有 backing、额外日志和独立回收副本不能因此免费。预先存在且真正只读的系统/工具输入按既有合同处理，但不能把本批源码组装、制作/暂存副本、构建或新后台写入改名为“预装环境”排除。准备期和正式 I5 必须分别验收，不能相互替代。

## 当前 Mac/UTM 为什么不能放行

| 对象 | 已有证据与机制边界 | 关闭要求 |
| --- | --- | --- |
| guest 根/var、EFI、swap、系统 tmpfs | 10 月 9 日历史盘点有可写根/EFI、约 2.584 GiB swap；used=0 不证明禁用；这些不是当前重查结果 | 启动前约束全部可写层、固件状态、换出和系统临时空间；首次启动写入也须计费 |
| backing、快照、介质制作/暂存 | 全设备与独立副本账本已设计；没有实际 hard limit/readback/拒绝证据 | 精确底层对象和元数据上限、并存副本峰值、配置前后身份及超额拒绝 |
| UTM/QEMU 状态、宿主全局日志、crash | 路径与生产者尚未完整绑定，当前覆盖裁决保留 unknown | 包括 VM 目录之外的生产者，不能仅关闭一项 debug log 或清空旧日志 |
| macOS swap | guest 内禁用 swap 不控制宿主换出；现有证据没有本次进程和关联系统写入的完整硬上限 | 能核验的约束机制与全程拒绝/回收证据；不将“内存够用”当作禁止换出 |
| 全部域的组合 | 单项声明与有限离线测试已经通过，完整物理承载未通过 | 每项同时成立、归属不重叠且都落入获批包络后，才可评审环境验收 |

Apple 的 [APFS 卷文档](https://support.apple.com/en-asia/guide/disk-utility/dskua9e6a110/mac)把 quota 定义为单卷分配上限；[虚拟内存说明](https://support.apple.com/en-ie/guide/mac-help/mh11852/27/mac/27)说明内存数据可换出到磁盘。工程推论是：只给 VM/证据所在卷设置 quota，不能证明其他系统卷写入也受同一额度约束。本次未找到并验证可覆盖当前整条 Mac/UTM 链的配置，所以不把“部分机制存在”提升为完整可行。

[UTM 磁盘文档](https://docs.getutm.app/settings-qemu/drive/drive/)还说明导入某些镜像会复制并转换为 QCOW2，APFS 上创建的 raw 镜像也可能是稀疏文件。这支持继续核对真实导入路径、并存副本和底层分配，不能把界面填写的镜像容量直接当作全部宿主写入上限；未在当前 VM 上实查该行为。

加大预算但仍没有硬机制，仍然无法证明有界；把目录搬到外置盘、使用稀疏镜像、在 Mac 上再套一层 Linux VM、运行后删除、关闭 guest swap，都不能单独关闭此缺口。本包不操作系统 swap/crash 策略，也不建议在日用 Mac 上靠压缩系统卷可用容量制造实验限额。

## 真实 FD loader 的信任边界

目标是使实际执行的有限库源码与本次获审 bytes 相同，并保证加载失败可以在原预算内被外部父进程停止。它不是通用 Python 沙箱；源码即使摘要匹配，仍必须是已审阅并获本次授权的程序。描述符和介质自带摘要不能互相认证自己。

可信基座必须在本次启动前具备：固定解释器/标准库/共享库、固定最小 launcher 与父监督 P、固定 loader、授权锚点及只读系统承载。它们的来源、版本、bytes/摘要、部署和物理约束属于后续独立准备包。单次授权锚点绑定 UUID、nonce、有效期、目标配置/介质 image、delivery 摘要、可信基座 revision/摘要及预算；不得只从待加载的 `delivery.json` 读取授权。自制签名或自研密码机制不属于本设计。

P 必须在读取、解析或编译 library 之前开始计时和监督。推荐把加载阶段放入其持久子进程 N：N 使用可信 loader 验证并消费库，再在同一进程创建唯一 native FD owner，继续 init/readback/cleanup/close；S/W 仍由既有任务监督逻辑管理。加载阻塞由 P 处理，N 死亡后 P 只保留事实和未确认状态，不重建 owner 按路径清理。

**不能直接把现有七模块 ZIP 加入 `sys.path` 后调用 `run_native_guest`。** 该函数目前在库加载之后才建立 guest 时钟和 N；其 syscall 路径明确仅允许注入。真实接入需要把已有 P/N 职责整理成可信基座 P 与 owner-only 库入口的明确接口，复用现有停止、登记、回收和报告逻辑，不能额外套一套独立 runner 或默默增加 reap 槽。本包只规定职责，不实现拆分或放宽当前拒绝。

真实 N 在完成 init 后才能构造绑定该次对象的 boundary/guard/exporter；固定工厂及任务入口必须属于获审源码闭包，不能继承在对象尚未创建时构造的注入 adapter，也不能把 factory/callback 放入控制面。S 只获得既有白名单能力，W 不继承 library 或 native 所有权 FD。

N 必须使用无既有项目模块缓存的执行上下文，避免继承 P 已导入模块后直接命中 `sys.modules`，绕过实际库 bytes。P/N 的加载前内存、PID、FD、输出及换出限制必须预先建立；不能等库执行后再创建 cgroup。当前任务 cgroup 的 512 MiB 父限及 64/384 MiB 子限并不证明加载前 P/N 已受控，剩余算术空间也不能默认当成 loader 额度。

## 两阶段身份合同

第五包的候选 `expected.json` 以及 `library_expected` 含 `dev/ino/mount_id`。它们适合绑定显式提供的同次离线观察，**不能作为跨 reboot 的稳定介质身份**。把上次 mount ID 写进启动前只读包，或在本次启动后重写只读包来匹配，都不成立。

| 阶段 | 应绑定的内容 | 使用限制 |
| --- | --- | --- |
| 启动前稳定预期 | 本次 UUID/nonce、固定路径、获审文件/介质摘要、只读承载要求、目标设备/介质的可核验稳定标识、预算和可信基座 | 后端必须证明稳定标识与实际挂载介质的关系；没有可用稳定属性就拒绝，不能伪造 fs UUID 或依赖设备序号 |
| 本次启动观察 | 当前 boot/调用身份、dev/ino/mount ID、文件类型/权限/nlink、挂载/文件系统身份及完整容量；固定 FD 的前后读取事实 | 只对本次调用有效；与稳定预期及授权锚点共同核对，再产生供 NativeGuestInitialization 消费的运行时 expected |

建议后续使用**独立的真实加载/交付 scope**表达这一区别。六个固定交付文件的角色和小描述符形态可保留，但不能把原 `expected.json` 的三个动态身份对象直接改成新语义而复用旧 scope。旧四模块、七模块候选、旧 source checker 与现有注入证据均保持历史含义；新 scope 的精确字段和消费者变更须在实现前评审。

运行时 expected 由可信 N 的预加载观察生成，并在 backend 操作前后独立重开核对；不接受库代码自报身份来覆盖预期。观察通过有界内部 IPC 绑定 P 的本次票据，不新增未计费的 guest 文件。库介质始终与 APT、初始化根、cgroup 承载分离；本次绑定不承诺跨启动数值恒定，也不把同进程二次读取称为外部来源认证。

## 加载状态与拒绝合同

所有状态只前进一次；失败立即终止任务准入，收尾保留首因。加载完成不产生工作租约。

| 状态 | 必须完成的动作 | 拒绝或取消后的事实 |
| --- | --- | --- |
| `ADMITTED` | P 已核对单次票据与完整前置，计时已开始；N 在加载前约束内启动 | 未得授权或父监督不存在时不读/执行库；重复 execute 不重试 |
| `PINNED` | N 从固定可信祖先逐级打开 library 根，验证唯一只读挂载及本次身份；目录精确包含六文件 | 禁止链接、别名、嵌套挂载、未知成员、可写源和身份变更 |
| `SNAPSHOT_VERIFIED` | 对六文件一次固定 FD 打开、受限读取并 hash，检查 EOF/长度和前后 fstat；得到不可变 bytes 快照 | 短读、增长、替换、摘要不符、非普通文件、nlink 非 1、宽松权限均失败 |
| `MODULES_VERIFIED` | 从已验快照解析 canonical ZIP，核对有限成员、源码、依赖闭包与 entry | 不执行未完成全量校验的成员；没有动态补下载或按环境补依赖 |
| `LOADED` | 仅由可信 loader 将已验成员 bytes 装入有限模块映射，进入唯一 owner-only 入口 | 语法/导入/资源/取消错误终止；不得回退路径导入或旧 program |
| `NATIVE_READY` | 同一 N 完成 native init 与独立 readback，P 接收登记与完整事实 | 只有这里之后才允许现有 transport 核对槽并传递初始租约；loaded 不等于 ready |
| `TERMINAL` | 收尾关闭 loader FD/清除不再需要的源快照；native 对象依原所有权协议处理 | 无报告、强杀、未确认 reap/cleanup 均明确保留；不得补造成功收据 |

文件打开合同：祖先以目录 FD 固定，逐段禁止符号链接；进入预期 library 挂载点后，其下文件使用相对固定名，禁止越界、magic link 和再次跨挂载。可评估 Linux `openat2` 的 `RESOLVE_BENEATH/NO_SYMLINKS/NO_MAGICLINKS/NO_XDEV`；`NO_XDEV` 只用于已进入 library 根后的解析，不能把进入预期挂载本身也无条件拒绝。若目标内核/绑定不支持所选精确机制，停止并单独评审，不能静默改成普通路径 open。[Linux openat2 手册](https://man7.org/linux/man-pages/man2/openat2.2.html)。

在任何源码执行前，全部六文件已形成并验证不可变 bytes 快照；之后只消费该快照。根和文件 FD 保留到验证、加载及加载后身份复核结束，随后明确关闭，不交给 S/W。发生路径/挂载变化时拒绝报告成功；不得按名称再开文件作为运行输入。已固定 FD 和 hash 不阻止恶意特权方改写底层设备，可信环境和无并发介质修改仍是前置条件。

优先设计为标准库 `ZipFile` 对已验内存快照读取，有限模块 loader 消费 bytes；不解包到磁盘，不使用 archive 路径作为 `sys.path`，不使用 `/proc/self/fd/N` 字符串代替严格的 FD 所有权合同。`ZipFile` 接受 file-like 对象，而 `zipimporter` 的接口基于 archive 路径；这说明二者消费方式不同，不等于内存 loader 已实现或已经安全。[Python ZipFile](https://docs.python.org/3.13/library/zipfile.html)、[zipimport](https://docs.python.org/3.13/library/zipimport.html)。

ZIP 只允许本次清单中的源码与内置 manifest：继承 `ZIP_STORED`、固定排序/时间/权限、非 ZIP64、无额外字段/注释、无自动 `__main__` 的 canonical 规则；拒绝重复名、路径穿越、压缩/加密、`.pyc`、native extension、链接、未知成员、未声明尾部 bytes 和重叠/矛盾记录。先核对固定成员集合与每项长度，再取成员内容；不能依赖 `zipfile` 自动规范化路径或“取最后一个同名成员”。

模块导入合同：项目模块只能命中已验固定映射；未知项目名和缓存污染失败，不能落回安装目录。标准库及其二进制扩展只能来自可信基座的固定只读来源，其版本/依赖须另行绑定；禁用用户 site、`.pth`、环境注入、工作目录导入和 bytecode 写入。候选启动策略使用固定 `-I -S -B`，并核对运行时状态；这些选项不是 OS sandbox。[Python 启动选项](https://docs.python.org/3.13/using/cmdline.html)。

可信启动使用精确可执行文件与参数、最小环境，不经 shell；动态链接器注入变量也不得继承，不能以 Python 的 `-I` 代替这一要求。模块的诊断 origin 使用绑定摘要的非文件路径标识，失败报告不得为显示源码行再次按原路径读取。

实际源码编译/执行只发生在受审可信 loader 内，对通过全部检查的有限成员进行。现有纯校验器仍不得执行 supplied bytes；不能为了实现 loader 把旧 AST 检查对任意 `exec/importlib` 的拒绝整体放宽。有限 loader 的例外、完整源码和测试须单独绑定新执行合同，不接受 caller 传来的函数、任意 argv、路径或 Python 字符串。

## 资源、证据与兼容

| 项目 | 设计约束 |
| --- | --- |
| 原始 bytes | 小描述符不超过既有 48 KiB；库 ZIP 不超过 8 MiB；单源码不超过 2 MiB。delivery 与 library manifest 各不超过 256 KiB、isolation 不超过 8 KiB、APT manifest 不超过 64 KiB；新稳定 expected 建议限 8 KiB。六文件合计上限 9 MiB 是候选加载限制，不是新增存储额度 |
| 内存与 FD | ZIP 快照、成员副本、编译对象、解释器/标准库、fork/COW 峰值及 IPC 均须计入预先建立的 P/N RAM/PID/FD 限制；不能用 9 MiB 文件上限推导 RAM 只需 9 MiB。具体硬值须与所选环境一起冻结；未数值化不得执行 |
| 写入与换出 | 无解包、`.pyc`、用户 cache/temp 或默认日志写入；原子源副本/诊断仍须计费。noswap tmpfs 及进程换出约束分别核验，guest 约束不代替宿主 swap 边界 |
| 时间 | P 接受调用、启动 N、加载、init/readback 共用原 guest 初始 6 秒窗口；后续 active 528、cleanup 2、reap 2、output 2 秒不额外扩张，总计 540。可信 P 自身的启动仍落在宿主 active/600 秒和整包 897/900 秒内；不能在 import 后重置计时。性能不足须失败并重新评审，不能自动加时 |
| 输出 | 沿用现有 export 总上限、原生 facts 128 KiB 和宿主报告/证据限额；loader 事实必须在其中分配。错误输出有界且保留阶段/首因，不导出源码、原始包数据库或私密输入 |
| 最少加载证据 | 可信基座与授权锚点摘要、delivery/ZIP/成员摘要、稳定预期与本次观察的关联、实际消费摘要、阶段耗时、FD 关闭、PID/退出/reap、首因/cleanup 错误；未发生的阶段留空，不补齐成功事实 |

[Linux tmpfs 文档](https://docs.kernel.org/filesystems/tmpfs.html)明确默认允许换出，并提供 `noswap`；[cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)规定 memory/swap 控制，但 memory.max 在某些情况下可能短暂超出。机制资料不是当前目标内核的实际保证，也不是整个宿主新增存储的硬上限证明。不能把进程 RAM、tmpfs 存储额度和宿主磁盘预算混为一项或重复相减。

现有 `bundle.validate_delivery` 是宿主纯校验入口，依赖 plan/RPC 等宿主模块，不在七模块 guest 闭包内。实现包须划清可信 loader 的有限格式校验与宿主物理/授权评审，可提取共享的纯格式规则并重新绑定源码；不能偷偷导入整套宿主依赖或复制另一份漂移的校验口径。

真实版本不能复用当前 `backend_kind=injected-offline` 的成功语义，也不能仅删掉 `LinuxNativeSyscalls` 拒绝就称为接入。必须绑定实际 boundary/guard/subreaper、固定只读准备任务、外部工具身份和真实来源事实。新增 scope 的旧消费者应明确拒绝；是否扩展现有 receipt 必须由需要保存的字段决定，不在本设计中提前升级持久化协议。

`execute-native/native-ready` 的真实 JXA 适配仍保持 STOP。内部 ready pipe 不是 UTM 已支持的跨主客通信通道；真实适配必须另证单次调用句柄、ready 取得方法和文件槽读回，不能通过新增未审服务/状态文件、重试 execute 或改变旧 ACK 槽语义偷偷补齐。所选承载若不再使用 UTM，也须交付等价的单次执行与回收合同。
