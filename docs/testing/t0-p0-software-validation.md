# 三节点软件探索与验证规范

## 用途与边界

本文记录 D0 阶段已经完成的最低成本 A—B—C 探索性探针，并约束后续验证设计。正式工作顺序、候选方案和决策门以[D0/P0 软件工作计划](../status/d0-t0-p0-plan.md)为准。

## 当前状态

2026-08-20 的探针运行早于正式计划和消息设计，只证明普通 Linux/Ethernet 容器环境能够承载三节点测试。它暴露了确认认证、状态语义、持久化、故障 profile 和证据格式等未决问题，因此登记为 `SW-EXP-001`，只作为需求发现证据，不作为 `SW-V*` 或 P0 阶段验收。

在工作计划 `SW-G0..G3` 完成、`SW-G4` 获得授权前：

- 不扩展 `tools/t0/`、不新增故障注入和密码依赖；
- 不把当前 JSON envelope、固定路由或 snapshot 状态当作产品设计；
- 不重新运行脚本来替代文档评审；
- 只允许修正文档或处理阻断评审的明显缺陷。

探针只涉及普通 Linux/Ethernet 语义上的三节点转发和恢复，不冻结生产语言、容器运行时、协议线格式、持久化格式、密码库或量产技术栈。

明确非目标：

- 不采购、连接或发射 HaLow 硬件，不改变监管域、功率、带宽或天线配置；
- 不验证距离、射频吞吐、媒体体验、功耗、温升、体积或法规合规；
- 不把 Docker bridge 等同于 802.11s、HaLow 或真实半双工空口；
- 测试载荷是合成明文；在[端到端加密候选评审](../security/e2ee-candidate-review.md)完成并获确认前，不验证或宣称 E2EE；
- `tools/t0/` 的 `version: 0` 信封和 JSON 状态只属于测试工具，不形成公共协议或迁移承诺。

## 2026-08-20 本机盘点

- Docker 29.4.0 已存在，当前 context 为 OrbStack，daemon 运行于 `aarch64`；
- Docker buildx 已存在，本地只有 PostgreSQL 镜像，但 T0 使用 host Go 编译加 `scratch`，无需拉取镜像；
- Go 1.26.3 已存在，只用于构建测试工具；
- Colima 不存在，本轮不安装；
- `utmctl` 与多台停止状态的 Debian 13 ARM64 VM 已存在，但最低成本路线不需要启动 VM。

因此首选现有 OrbStack/Docker。若 Docker 后续不可用，第二选择是经单独授权启动一台已有 Debian VM，在 VM 内使用三个 network namespace；若两者都不存在，再报告可用 Linux 主机或廉价 Linux VM 方案，不自行安装或采购。

## 拓扑强制方式

测试脚本创建两个独立、仅内部可达的 Docker bridge：

```text
A ── radishlink-t0-ab ── B ── radishlink-t0-bc ── C
```

- A 只加入 `ab`，C 只加入 `bc`，两者没有共享 L2 网络；
- B 同时加入两张网络，是唯一可用下一跳；
- 脚本分别从 A、C 对另一端执行负向连接探测，并从 B 对两端执行正向探测；
- 固定路由只服务此测试，不代表未来的邻居发现或路由协议。

## 探索性入口与副作用

```bash
./scripts/run-t0-three-node.sh
```

脚本会用唯一 run ID 构建一个临时 `radishlink/t0-node` 镜像，创建两张内部网络和 A/B/C 三个短生命周期容器，在系统临时目录保存三节点状态，并在存储转发用例中重启 B 一次。它不拉取镜像、不访问互联网、不使用 `NET_ADMIN`、不修改 macOS 网络或防火墙配置，通常一分钟内结束。

该命令不是默认门禁。后续重跑必须先有已评审的目的、profile、预期结果与证据保存方式，并按外部状态规则重新说明副作用和清理方式。

正常结束、失败或收到 `INT`/`TERM` 时，trap 会删除本轮三个容器、两张网络、临时镜像和临时状态目录。若进程被 `SIGKILL`，先用以下只读命令按 label 查明精确资源，再逐项清理，不对宽泛名称或其他项目资源执行删除：

```bash
docker ps -a --filter label=org.radishlink.t0.run
docker network ls --filter label=org.radishlink.t0.run
docker image ls --filter label=org.radishlink.t0.run
```

## 已有探索性检查与待设计验证

### SW-EXP-001：2026-08-20 探索性探针

已执行：

1. A 与 C 直连负例、B 到两端正例；
2. A 以两个 forwarding hops 经 B 向 C 发送，A 收到来自目的端流程的确认；
3. 相同消息 ID 重放后，C 的用户交付计数仍为 1；
4. 一个 forwarding hop 在 B 耗尽，C 在观察窗内没有交付；消息 lifetime 到期后从 A 队列移除；
5. C 断链后 B 持久保存消息；再断开 A 排除重传回填，B 重启仍保留队列；A/C 恢复后完成交付和确认，B 释放副本。

这里的“目的端确认”只证明测试状态机的端到端语义。它没有密码认证，恶意中继仍可能伪造，不能代替 P0 的可验证确认安全要求。

`SW-EXP-001` 的 `PASS` 仅指上述脚本断言通过。由于运行前没有完成 `SW-G0..G3`，它不能升级为阶段验收，但可以作为后续设计的输入和回归参考。

### SW-V1：确定性故障注入矩阵（待 `SW-G3`）

在不新增特权和第三方依赖的前提下，为链路加入带固定 seed 的用户态故障代理，逐项而非同时注入：

- 延迟：每跳固定值与受控抖动，记录提交、目的端交付和确认时间；
- 丢包：按固定序列丢弃数据与确认，验证重试和最终去重；
- 限速：按字节预算限制，覆盖 1 B、1 KiB 和 16 KiB 合成载荷；
- 乱序：固定窗口重排，验证去重状态和确认不提前释放未交付内容；
- 重复：在 A→B、B→C 和确认回程分别复制，交付计数始终为 1；
- 断链：分别断开 `ab`、`bc`，验证 custody 所在节点、恢复和超时边界。

每一种 profile 都需要保存 seed、参数、软件版本、结果与失败时间线。`SW-V1` 通过仍只属于 Docker/Ethernet 仿真。

### SW-V2：资源与恢复负例（待 `SW-G1/SW-G3`）

- B 存储配额耗尽、状态文件损坏、只读数据目录和部分写入；
- A/B/C 分别重启，确认未确认消息不被误报送达，已交付消息不复活为第二次用户交付；
- wall clock 回拨和跳变，验证 relative lifetime/单调计时设计；
- 未知协议版本、超长字段、未知 ID、无路由与高速新 ID 的拒绝和来源配额；
- 1000 条合成消息的延迟分位数、重复交付率、队列上限和残留状态。

### SW-V3：经确认的 E2EE 集成（待 `SW-G2`）

只有密码协议、实现库、许可证、平台和持久状态策略经评审确认后，才用库产生的认证密文替换合成明文，并增加篡改、重放、乱序、状态回滚、密钥变化与 B 不可解密负例。该阶段通过后才能形成“Docker 三节点 E2EE 软件验证”结论，仍不能外推到无线或量产环境。

## 结果口径

- `PASS` 只覆盖脚本实际执行的 profile 与断言，不自动表示工作计划、`SW-V*` 或项目阶段通过；
- 命令退出 0 之外，还要确认脚本打印最终 `T0 PASS` 且没有残留本轮资源；
- 失败时保存三个节点日志和退出码；日志只包含合成 ID、路由结果和错误，不记录正文或真实身份；
- `SW-*` 结果只进入软件工程证据，不进入 HaLow 距离、媒体、功耗或法规数据集。
