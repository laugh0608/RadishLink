# RadishLink 硬件策略

## 结论

首个可行方案不是“ESP32-S3 + HaLow 模块直接做完整产品”，而是：

> 具备硬件视频能力的 Linux 应用处理器 + MM8108 HaLow 候选模块 + 独立 2.4 GHz Wi-Fi/BLE + 可选 ESP32-S3 辅助 MCU。

这样可以先用成熟系统验证路由、端到端安全和媒体，再把功耗、体积与成本收敛到工程样机。

## 为什么 ESP32-S3 不作为中继主控

ESP32-S3 官方能力包括双核 240 MHz、2.4 GHz 802.11b/g/n、Bluetooth LE、最高 16 MiB PSRAM 的模块选择、摄像头/LCD/I2S 外设和 OTA 支持。它适合交互、传感、低功耗控制和部分音频，但存在以下项目级限制：

- 不包含 802.11ah/HaLow 射频；
- 接入 MM8108 所需的驱动、接口与官方平台支持需要单独验证；
- 没有 Linux 上成熟的多路径、持久队列、WebRTC/GStreamer 和系统升级生态；
- 不具备适合目标中低码率实时视频的通用硬件编码与内存余量；
- 同时承担 HaLow、2.4 GHz 接入、加密、图片和音视频会显著放大集成风险。

它可以进入最终设备，但职责应限制为低功耗域。首次刷写或救砖仍保留有线/治具；正常开发版本支持签名 OTA 和回滚，因此 Mac 日常不必一直插线。

## Wi-Fi HaLow 与 MM8108

MM8108 是值得验证的候选：

- IEEE 802.11ah，1/2/4/8 MHz 信道；
- 厂商标称最高 PHY 速率 43.33 Mbps；
- 支持 USB 2.0、SDIO 2.0 和 SPI 主机接口；
- 支持 WPA3，模块覆盖 850–950 MHz 可编程射频范围；
- `MM8108-MF15457` 模块约 11 mm × 10 mm，适合后续集成。

但这些事实不等于 500 m 视频、多跳吞吐或中国大陆免许可可用已经成立。802.11s 的厂商产品文档仍标为实验性，所有距离和并发能力都必须按目标地区重测。

## 原型平台比较

| 平台 | 优点 | 局限 | 推荐用途 |
| --- | --- | --- | --- |
| `MM8108-EKH01-01` | Raspberry Pi 4 + MM8108 + Linux/OpenWrt，HDMI、USB、Ethernet、音频，最接近应用开发机 | 体积/功耗非产品级；近距 2.4 GHz 并发需确认或加独立适配器 | 首选三节点应用与媒体 POC |
| `MM8108-EKH19` | MM8108 USB 参考适配器 + GL-MT3000 路由器，2.4 GHz/5 GHz 接入方便 | 更像桥接/路由验证平台，不是完整手持终端 | 无线链路、手机接入和 USB 集成验证 |
| `HaLowLink 2` | MM8108、2.4 GHz、OpenWrt、Ethernet 一体，最快验证 AP/STA/802.11s | 32 MB NAND、路由器形态，Mesh 为实验性；公开支持地区不含中国大陆 | 快速射频/拓扑 POC，不作为应用主机 |
| `MM8108-EKH05-01` | STM32U585 + MM8108 + BLE，低功耗 MCU 路线 | 更适合传感/静态图像，不适合完整实时视频终端 | 后续低功耗节点或 MCU 集成研究 |
| 普通 ESP32-S3 开发板 | 便宜、屏幕/音频外设丰富、OTA 方便 | 无 HaLow，不能证明长距媒体 Mesh | 辅助 MCU 和独立 UI/电源实验 |

## 推荐 POC 拓扑

### 路线 A：应用优先

三台 `MM8108-EKH01-01`，每台作为完整 Linux 节点。必要时为每台增加已验证 OpenWrt/Linux 驱动的独立 2.4 GHz USB Wi-Fi 适配器，让手机接入与 HaLow 同时工作。

优点是应用、加密、媒体和路由都在同一主机；缺点是采购成本、功耗和近距无线并发需要核实。

### 路线 B：射频与应用解耦

三台 `HaLowLink 2` 或 `MM8108-EKH19` 负责 HaLow 与近距 AP；每台通过 Ethernet 连接一台普通 Linux SBC 运行 RadishLink Core。

优点是无线和应用可分别替换，最容易定位性能问题；缺点是台架更大，不能代表手持体积。

如果预算只够一条路线，优先路线 A。若首个测试地区不支持相应 SKU，则暂停 HaLow 采购，先在三台普通 Linux 设备或虚拟网络完成 P0 软件闭环。

## 工程样机选型门槛

应用处理器/SoM 至少需要：

- 64-bit Linux、长期内核/BSP 和可信启动；
- 2 GiB RAM 起步，8 GiB 以上可靠闪存或 eMMC；
- H.264 或选定编码的硬件编码/解码，能够维持 360p/15 fps 并留出加密余量；
- USB 2.0 High-Speed 或 SDIO 给 HaLow，独立 SDIO/PCIe/USB 给 2.4 GHz/BLE；
- MIPI CSI、显示、I2S/PCM、USB、充电与电池计量接口；
- 空闲、语音和视频三种状态的可测功耗与热设计；
- 可获得模块、参考设计、法规材料和 3–5 年供应计划。

不在 POC 前根据纸面参数选择最终 SoC。Raspberry Pi、NXP i.MX、Rockchip 等只在获得编解码、驱动、功耗和供应证据后进入决策矩阵。

## 天线与结构

- HaLow、2.4 GHz/BLE 和可选 GNSS 使用明确隔离的天线与净空；
- POC 使用套件随附、与监管域匹配的天线，不擅自更换高增益天线或外接 PA；
- 背包、人体遮挡和握持方向是必须测试的产品场景，不能只测架高天线；
- 金属外壳能优化某些参考平台并不代表适合手持，最终需联合天线、屏幕、电池和散热设计；
- 位置能力首期可用手机/GNSS 记录测试轨迹，不用 RSSI 输出虚假精确距离。

## 电源目标

在获得实测前只设预算门，不承诺续航：

- 待机监听与低频中继：整机平均目标低于 1.5 W；
- 文字活跃/附件间歇：目标低于 3 W；
- 连续语音：目标低于 4 W；
- 连续视频：目标低于 7 W，且外壳可触温度受控。

若 POC 证明 Linux + 双无线无法进入目标预算，需要评估双处理器休眠架构，而不是用降低安全性或关闭中继来掩盖问题。
